# Recommended future agent orchestration

**RECOMMENDED — not historical fact.** Keep the team small. For the immediate static cover task, use a lead plus at most two independent reviews; do not spawn a swarm.

## Sequence and scopes

### Lead / integrator (required)

- Own objective, scope, owner updates, source inspection, implementation and integration.
- May edit only the explicitly approved cover and its supporting docs/assets. Do not touch tokens, dependencies, config, GraphMARL claims or unrelated routes.
- Reconcile review feedback, inspect the integrated desktop and 762px page, run focused checks, report exact changed files and evidence.
- Stop after one RANGraph cover is reviewable.

### Project-evidence reviewer (parallel, read-only)

- **Objective:** Identify which RANGraph visual relationships/materials are supported by checked-in fixture/source and what must be disclosed as schematic.
- **Scope:** Read-only `C:\RESEARCH\RANGraph` and V3 RANGraph docs/model/instrument.
- **Forbidden:** No code/assets edits, no inferred edges, no claims of Python/browser parity without checking.
- **Evidence:** Cite paths, fixture records, transformation and export boundaries.
- **Deliverable:** Short facts/unknowns table and one recommendation for a truthful visual motif.
- **Stop:** When supported facts and presentation caveats are clear.

### Design critic (parallel, read-only)

- **Objective:** Review the one cover hypothesis for hierarchy, authenticity, crop and clarity at desktop/762px.
- **Scope:** Read-only approved captures and current design docs.
- **Forbidden:** No changes, no unsolicited redesign, no new effects/tokens.
- **Evidence:** Annotate actual screenshots or precise source findings; separate visual judgment from functional proof.
- **Deliverable:** Pass/block plus the few most important corrections; state untested behavior.
- **Stop:** One bounded review pass.

### QA/accessibility/performance reviewer (sequential after integration)

- **Objective:** Test the integrated result and responsive behavior.
- **Scope:** Read-only current code/browser/tests. If a defect is found, send it to lead rather than editing the same files.
- **Checks:** Desktop and exact 762 CSS px, overflow/crop, scroll, focus and keyboard, touch, reduced motion/Pause if motion remains, loading/failure, browser console, focused tests/typecheck/build as appropriate. Measure performance before claiming a bottleneck.
- **Deliverable:** Reproducible steps, browser/viewport, exact commands and outcomes, screenshots and limitations.
- **Stop:** Once requested scope is evaluated; no broad exploratory polish.

## Parallelization and authority

Evidence and design review can run in parallel because both are read-only and non-overlapping. Implementation waits until the lead has source facts and a specific cover hypothesis. QA waits until integration is stable. The lead alone resolves disagreements and communicates whether the owner accepted the result. A screenshot does not certify interaction, and a build does not certify design acceptance.
